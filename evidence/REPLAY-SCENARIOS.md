### 12-irreversible-slow-submit-retry-refused -- A slow irreversible submit is NOT retried automatically

The most important safety case in the project. The submit POST stalls for 30s, so the confirmation screen does not appear within the step budget and the transient-slow-load handler matches. Because the step is classified irreversible, the retry is refused and a human is asked instead -- we do not know whether the first submit took effect. Ground truth: it had. Exactly one sub-account was created, which is what a retry would have made two.

```
ESCALATED human-decision -> abort  at step 11-click-submit-request
```

expected `escalated`, got `escalated` -- match

### 13-recovered-slow-load -- Recoverable: a load that overruns the step budget

A 16s stall exceeds the 10s step budget, so the checkpoint fails and the failure-code-guarded transient-slow-load handler fires. On re-attempt the checkpoint is found already satisfied, so the click is not repeated. A 9s stall (inside budget) needs no handler at all -- condition polling absorbs it.

```
SUCCESS  member.read-savings-balance@1.0.0  outputs={"savingsBalance":8241.77}  26791ms

recoveries:
  transient-slow-load (retryStep) at 07-click-search: backing off 3000ms (attempt 1/1)
```

expected `success`, got `success` -- match
